# Installed Package

Inventory of the features installed in this template and whether each one
actually works yet. Says what exists — not how it works. Follow the doc column
for that.

**The template ships movement, camera look and one action button: Jump.** On a
touch client an on-screen stick and Jump button are live. Several systems below
are complete and placed but deliberately unbound, because a starting template
should not present a screen of buttons. Each says what turning it on costs.

| Feature | Status | Where it lives | Doc |
|---------|--------|----------------|-----|
| Third-person player character | **Live** — `PlayerCharacter` is the world's player template, set on `StartingWorld`'s player config. Movement, auto-face rotation, kinematic locomotion (on the `KinematicCharacter` simulated child), ground detection, soft collision and animation are all placed and running. | `Templates/PlayerCharacter.hstf`, `scripts/Character/` | `Docs/PROJECT_SUMMARY.md` |
| Jump | **Live — the only bound button.** `JumpInputConfig.inputconfig` is assigned to `PlayerActionController.jumpInputConfig` on the scene's `PlayerInputServices` entity, so the on-screen Jump button binds and routes to `CharacterStateMachine.handleJumpClick()` / `handleJumpRelease()`. `JumpAbility` is on the player template and the `Jumping` state is registered. The legacy `JumpClickEvent` handler remains for wiring a custom HUD. | `space.hstf`, `Templates/PlayerCharacter.hstf`, `scripts/Character/Abilities/JumpAbility.ts` | `Docs/PROJECT_SUMMARY.md` |
| Player input | **Live, on two cooperating paths.** `scripts/Input/PlayerActionController.ts`, on `PlayerInputServices`, owns the keyboard/gamepad buttons; they are declared in one `defineActions()` table, and the movement axis is the one action with no config asset, so it is subscribed directly in `onStart()`. The on-screen path is separate — see the touch-controls row below. The engine allows a single subscriber per action, so keeping the buttons in one table is what prevents two components claiming the same one. **Camera look is the exception to "all input lives here":** the right-stick/mouse axis is subscribed by `CameraManager` on the `Camera` entity, and a drag on empty screen is handled by `TouchCameraLook`. | `space.hstf`, `scripts/Input/`, `scripts/Camera/CameraManager.ts` | `Docs/PROJECT_SUMMARY.md` |
| On-screen controls | **Live, portrait split by default.** A `TouchControl` entity carries the on-screen HUD: `TouchJoystick` draws a floating stick that appears wherever a finger lands in the movement zone (the bottom half in portrait, the left half in landscape), `TouchCameraLook` takes the complementary half as a drag-to-look area, and `TouchControlsHud` draws the buttons on top. `TouchRouter` decides which control a given finger belongs to, so movement and camera can run on two fingers at once. They publish to `InputActionsManager` on `PlayerInputServices`, which also hides the engine's own joystick and gameplay controls so the two input paths do not compete. `ProjectControlsBridge` on `PlayerCharacter` turns the published Move and Jump actions into movement and jumps. Both zone components ship `landscape: false`. | `space.hstf`, `scripts/Input/`, `UI/` | `Docs/PROJECT_SUMMARY.md` |
| Object interaction and grabbing | **Code only — nothing is placed on either side.** Neither `PlayerCharacter` nor `BaseActor` carries an `Interactor` child, so nothing finds nearby targets and neither the contextual Interact button nor the Drop button appears. The object half is unplaced too: `SimpleInteractablePromptComponent` (makes an object respond and highlight) and `AttachableObject` (makes it pick-up-able and droppable) ship in `scripts/Interaction/` but are on no entity. It takes both halves — an `Interactor` child on the character (`InteractorComponent` + a Trigger body + a Layer3 sphere collider + `InteractionController` + `InteractionControlsBridge`), and the prompt/attachable components on an object. | `Templates/PlayerCharacter.hstf`, `Templates/Actors/BaseActorTemplate/BaseActor.hstf`, `scripts/Interaction/` | `Docs/PROJECT_SUMMARY.md` |
| Player melee | **Installed and coded, but NOT bound — enabling it is one property assignment, not new code.** `WeaponMeleeComponent` is on `PlayerCharacter` and the `melee` row exists in `PlayerActionController.defineActions()`, wired to `pullTrigger()` / `releaseTrigger()`. `MeleeAttackInputConfig.inputconfig` ships in `scripts/Input/`. What is missing is the assignment: `PlayerActionController.meleeInputConfig` on `PlayerInputServices` is empty, so the action is skipped and no button appears. Assign that asset and the swing, its cooldown and its GAS damage cone all work. **Do not author a new attack component for a melee request** — assign the property. | `space.hstf`, `Templates/PlayerCharacter.hstf`, `scripts/gas/weapons/melee/`, `scripts/Input/` | `scripts/gas/using-gas-system.md` |
| Click-to-move locomotion | **Installed and wired, but OFF by default — a one-property change.** `ClickToMoveController` is attached to `PlayerInputServices` and the navmesh it needs is live. What gates it is `LocomotionSettingsComponent.locomotionMode` on that same entity, which **ships as `Joystick`**. Set it to `ClickToMove` and tap-to-move works: a tap raycasts to the ground, snaps to the navmesh, pathfinds around obstacles and steers the character; a drag rotates the camera instead. The two modes are mutually exclusive — there is no value that runs both. | `space.hstf`, `scripts/Locomotion/` | `Docs/PROJECT_SUMMARY.md` |
| Character animation — base graph | **Live for locomotion and jump.** The player's animator runs `Standard_Character.animgraph`, and `CharacterAnimationController` drives `Speed`, `MovementDirectionYaw`, `IsGrounded`, `IsRecentlyGrounded`, `IsJumping` and the `JumpTrigger` event, so the `Grounded` blend space and the jump states play. Four attachment sockets (RightHand, LeftHand, Back, Head) are placed and follow the skeleton. | `Templates/PlayerCharacter.hstf`, `Assets/Default/Standard_Character.animgraph` | `Docs/PROJECT_SUMMARY.md` |
| Character animation — additive layers | **Installed and driven.** Five layers are mounted on the player's animator — `Airborne_Layer`, `Attack_Layer`, `Ranged_Layer` and `Take_Damage_Layer` (the last three masked to `human_upper_body.skelmask`), and `Death_Layer`. `CharacterAnimationController` drives all of them behind `playAttack()`, `playRangedAttack()`, `playTakeDamage()` and `setDead()`. It writes each attack layer's duration/cooldown before the transition (their exit gate is `state_finished AND <cooldown> > 0.1`, so an unwritten cooldown freezes the pose) and ramps the three masks by `Speed` — a swing at rest plays full-body, one at a run stays upper-body and the legs keep running. Every authored layer, state and variable name is spelled once in `scripts/animation/AnimationGraphContract.ts`. | `Templates/PlayerCharacter.hstf`, `Assets/AnimationGraphs/`, `Assets/masks/`, `scripts/animation/` | `Docs/PROJECT_SUMMARY.md` |
| Camera (all modes) | **Live** — `CameraManager` is on the scene `Camera` entity and is the only camera component. It starts in `ThirdPerson` (`cameraMode: 0`, auto-rotate, collision avoidance, angle smoothing) and switches to any of the ten `CameraModeType` modes via `setMode()` without adding or removing components. Only ThirdPerson is exercised by the current scene; the other nine are installed but unproven in this world. | `space.hstf`, `scripts/Camera/` | `Docs/PROJECT_SUMMARY.md` |
| Gameplay Ability System (GAS) | **Live.** The framework under `scripts/gas/` backs character health. `CharacterGASComponent` seeds a `health` attribute, clamps it, applies `state.dead` at zero and drives the death pose; it is on `PlayerCharacter`, and `ActorGASHealthComponent` extends it for NPCs. Component lookup matches on `instanceof`, so any damage source resolving `GASComponent` or `CharacterGASComponent` finds either. | `scripts/gas/`, `scripts/gas/CharacterGASComponent.ts` | `scripts/gas/using-gas-system.md` |
| GAS weapons, projectiles, targeting | **Melee is placed but unbound; hitscan and projectile are installed, not wired.** `scripts/gas/weapons/melee/` resolves a sphere overlap plus a facing arc at the moment of the press, and is on `PlayerCharacter` — see the melee row above for what binding it costs. Hitscan, projectile and the multi-weapon loadout are present but on no entity. `scripts/gas/weapons/targeting/Targeting.ts` walks up from a hit collider to the entity carrying the `GASComponent`. | `scripts/gas/weapons/`, `scripts/gas/projectiles/` | `scripts/gas/using-gas-system.md` |
| Player death | **Reachable through damage only.** `CharacterStateMachine.setDead()` enters a `Dead` state that blocks `MovementAbility`, `JumpAbility` and `AutoFaceRotationAbility`; `CharacterAnimationController` polls it to drive the death pose and refuses attacks, and `ClickToMoveController` cancels any active path. Gravity keeps running, so a character killed mid-air falls and settles. There is no death button; the way in is `CharacterGASComponent` applying `state.dead` when `health` hits zero. | `scripts/Character/State/CharacterStateMachine.ts`, `scripts/gas/CharacterGASComponent.ts` | `Docs/PROJECT_SUMMARY.md` |
| NPCs (Actor Framework) | **Live, but no NPC in the active scene.** `ActorSdkManagerComponent` is placed on `ActorFrameworkServices` and the behaviour library is installed, but `space.hstf` places no actor instance — placing one is up to you. `BaseActor` is the template to duplicate. | `space.hstf`, `scripts/Actor/` | `Templates/Actors/actorTemplatesRegistry.md` |
| Combat NPC template (chase + melee) | **Available, not placed in any scene.** `Templates/Actors/BaseActorTemplate/BaseActor.hstf` carries `ActorAnimatedAttackComponent`, `ActorTransformMoveComponent`, `ActorGASHealthComponent`, `ActorHealthStarterComponent` and `ActorPhysicalStaggerController`, and runs `Standard_Character.animgraph` with the same five additive layers as the player. It does **not** carry `ActorCombatStarterComponent`, so the bare template has no behaviour and just stands there — each placement adds it. It is also the template to duplicate for a new actor type. **Damage lands on the player:** melee damage requires a target carrying `CharacterGASComponent`, and `PlayerCharacter` has one. NPC-vs-NPC damage works too, since `ActorGASHealthComponent` extends `CharacterGASComponent`. | `Templates/Actors/BaseActorTemplate/BaseActor.hstf` | `Templates/Actors/actorTemplatesRegistry.md` |
| NPC health / damage | **Installed on the `CombatEnemy` (`BaseActor`) template.** `ActorGASHealthComponent` (extends `CharacterGASComponent`) tracks health and drives hit/death reactions; `ActorHealthStarterComponent` wires `DeathBehavior` and `StaggerBehavior`. Revive is not supported: `setHealthData` restores HP but warns that animation state does not follow, so the actor holds its death pose. Respawn rather than revive. | `Templates/Actors/BaseActorTemplate/BaseActor.hstf`, `scripts/Actor/Utilities/` | `Templates/Actors/actorTemplatesRegistry.md` |
| Hit and death VFX | **Installed, on no entity.** `ActorVfxOnHit` plays one effect when an actor is hurt and another when it dies. It needs both effect templates assigned, and neither the component nor any effect is placed. | `scripts/Actor/Utilities/ActorVfxOnHit.ts` | `Assistant/skills/` |
| Bot players | **Installed, on no entity.** `scripts/WorldsBotPlayer/` can spawn stand-in players from the world's player template and keep a target headcount filled, picking spawn points as it goes. Nothing places or starts it. | `scripts/WorldsBotPlayer/` | — none in project |
| Navigation / pathfinding | **Live, but far smaller than the floor.** `NavMesh` entity with a baked navmesh, profile and area-type assets, plus `NavMeshRebuildOnLoad` on `NavMeshServices`. `generationConfig.halfExtents` is `25, 10, 25` and the entity sits at `y = 5`, so the baked volume is 50×20×50 spanning x/z ±25 and y −5…+15 — **not** centred on the origin, and covering only the central quarter of the 200×200 m floor in each axis. Walking is unaffected; click-to-move and `CombatEnemy` pathing stop at that edge. Grow `halfExtents` before building out. | `space.hstf`, `NavMesh/`, `scripts/Navigation/` | `Docs/PROJECT_SUMMARY.md` |
| Camera collision test scene | **Present, not the active scene.** `Templates/Scenes/CameraTest.hstf` is a walls-and-cubes scene for exercising `CameraManager`'s collision avoidance. | `Templates/Scenes/CameraTest.hstf` | — none in project |
| Actor behaviour skills | **Installed.** The `implementing-actor-behaviors` corpus ships in-project, alongside the health-system skill. GAS is documented but is **not** a skill: `scripts/gas/using-gas-system.md` sits beside the code and is reached from this table, not from the assistant's skill catalog. | `Assistant/skills/` | `Assistant/skills/READE_ME_BEFORE_ADDING_SKILLS.md` |
| Primitive building-block templates | **Available** — cone, cube, cylinder, disc, plane, prism, pyramid, sphere, torus, wedge, ready to place. | `Templates/Primitives/` | — none needed |

## Notes

- The combat NPC template is `Templates/Actors/BaseActorTemplate/BaseActor.hstf`,
  and its root entity is named `CombatEnemy`.
- `Templates/Primitives/` spells the disc template `Dics.hstf`.
- Scripts carry a one-line version header, for example `// Camera Scripts v1`.
  It records which revision of that system you have, and CI checks it against a
  ledger. The files are ordinary source and are meant to be read and edited.
